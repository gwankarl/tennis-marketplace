# Tennis Xpress Working Rules

- At the start of each increment, inspect the relevant code, configuration, and tests before proposing changes.
- Begin each increment with a numbered task roadmap and a clear completion outcome.
- Provide manual implementation instructions for Task 1 only, then stop and wait for me to confirm completion.
- Keep task numbering across the increment. When I confirm a task, report progress briefly and provide instructions for the next task only.
- I apply all code changes manually. Do not create, edit, or delete files, install packages, run application commands, or run tests yourself.
- Include safe directory and file creation commands when needed. Never use commands that overwrite existing files.
- When a task creates or changes test files, provide the relevant focused test command for me to run after that task.
- Do not run or ask me to run routine lint, formatting, typecheck, build, or full test checks after every task.
- Provide the complete relevant verification commands once, at the end of the increment.
- Earlier checks are appropriate only when an actual error, dependency installation, migration, or unresolved compatibility issue needs immediate verification.
- For small changes, provide exact paths, inspected line numbers or ranges, code anchors, and replacement snippets. For substantial or scattered changes, provide complete replacement files.
- Do not continue to the next task until I confirm the current task is complete.
- Use the approved React, TypeScript, Node.js, and PostgreSQL modular-monolith architecture.
- Use one repository with frontend and backend npm workspaces.
- Treat specific frameworks, libraries, and versions as undecided until explicitly agreed.
- Keep business logic in domain modules and enforce authorization on the backend.
- Never include secrets in source code or committed files.
- Do not introduce features outside the requested scope.
- Do not create or update planning documents unless requested.
- Keep explanations concise and ask questions only when needed to complete the current task.
- Do not commit, push, or deploy unless explicitly requested.
- Keep backend routes and HTTP response translation at the HTTP boundary; keep business rules and expected errors in domain modules, persistence in repositories, and shared database/configuration code in their established locations.
- In the frontend, keep React Router modules in app/routes, feature-specific UI in app/features, genuinely reused UI in app/components, and server-only API/session helpers in app/lib using .server.ts filenames. Retain framework-required filenames and move existing files only when useful.
- Return API errors as { error: { code, message, optional details }, meta: { requestId } }; generate request IDs server-side and match x-request-id to the response envelope and request logs.

## Code Documentation Standards

- Use clear names and small, focused functions.
- Add comments to explain non-obvious decisions, business rules, constraints, and workarounds.
- Use JSDoc/TSDoc when it clarifies exported interfaces, important service contracts, side effects, or error behavior.
- Document security, transaction, concurrency, and idempotency assumptions near the relevant code.
- Do not comment obvious operations or repeat TypeScript types in prose.
- Keep comments accurate when providing code changes.
- Do not create separate documentation files unless requested.

## Naming Conventions

- Use kebab-case for custom file and directory names.
- Use PascalCase for React components, TypeScript types, and interfaces.
- Use camelCase for functions, variables, and properties.
- Name custom hook files `use-<name>.ts` and export hooks as `use<Name>`.
- Use descriptive backend suffixes where applicable: `.service.ts`, `.repository.ts`, `.schema.ts`, and `.routes.ts`.
- Name unit and integration tests `<name>.test.ts` or `<name>.test.tsx`. Verify browser behavior manually; do not add automated browser or end-to-end tests or tools.
- Use UPPER_SNAKE_CASE for environment variables and true module-level constants.
- Use snake_case for PostgreSQL tables and columns, with plural table names; map them to camelCase TypeScript properties.
- Preserve filenames required or conventionally generated by tools, including `AGENTS.md`, `package.json`, `root.tsx`, and React Router configuration files.
- Follow existing local conventions when extending code. Do not rename existing files without an explicit request.

## Manual Code Changes

- Inspect the current file before giving edits.
- For small changes, provide the exact path, current line numbers or range, the existing code to locate, and the replacement snippet.
- Include nearby context because line numbers may shift after earlier edits.
- If several edits affect one file, reference its original inspected version and explain the application order.
- For substantial or scattered changes, provide the complete replacement file, preserving unrelated behavior.
- For new files, provide safe directory/file creation commands and complete contents.
- Never invent line numbers. If the file cannot be inspected, say so and use an exact code anchor instead.

## File and directory placement

Before creating a file or directory, inspect the current structure and follow
the organization established by the completed backend/frontend rearrangement.
Do not recreate old paths or reorganize unrelated files.

### Backend
- Keep app.ts focused on composition and server.ts on API startup/shutdown.
- config/: environment and logging configuration.
- db/: shared database connection and database commands.
- http/: HTTP error translation and OpenAPI infrastructure.
- infrastructure/: reusable external-service adapters, such as SMTP transport.
- modules/<domain>/: domain-owned schemas, routes, services and repositories.
- Within identity, use the established registration, passwords, verification
  and sessions folders where appropriate.
- Keep verification-specific templates, queue logic and delivery behavior
  within the verification module.
- workers/: executable worker entry points; domain behavior stays in modules.
- drizzle/: generated SQL migrations and metadata. Preserve migration history.

### Frontend
- Preserve React Router framework files and route-module conventions.
- routes/: route registration targets, loaders/actions, headers and boundaries.
- features/<feature>/components/: feature-specific UI.
- features/<feature>/schemas/: form validation.
- features/<feature>/server/: feature-specific server orchestration/API calls.
- components/: UI genuinely reused across features.
- config/: environment configuration.
- lib/: reusable infrastructure, including the server-only API client.
- lib/security/: shared cookie, CSRF, origin and return-path handling.
- styles/: global styles; feature-specific CSS may stay with its feature.
- Keep server-only modules marked .server.ts and out of browser imports.

### Tests
- Follow each workspace's established unit/, integration/ and support/ layout.
- Classify tests by dependencies and boundaries, not filenames alone.
- Keep database-dependent integration tests separately discoverable from
  database-independent tests.
- Put fixtures/fakes in shared support only when reused.
- Ensure test files are discovered exactly once.

### Placement rules
- Create folders only when actual files need them; no empty future scaffolding.
- Keep small private helpers in their owning file.
- Avoid generic utils/, helpers/ or common/ dumping grounds.
- Extract shared code only when there is demonstrated reuse.
- Do not split files or add architectural layers merely for symmetry.
- Follow existing naming conventions and preserve framework-required names.
- Before a new domain or cross-cutting abstraction, propose its location and
  responsibility for agreement.
- If these rules conflict with the actual structure, flag the conflict before
  creating an alternative hierarchy.
